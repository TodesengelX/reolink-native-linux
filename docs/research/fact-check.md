# Fact-Check: Verified Claims

24 load-bearing claims from the research were adversarially verified by independent agents.

## ❌ REFUTED: Whether 'Balanced' is a distinct stream-quality option in the desktop Client — docs confirm only Clear (main) and Fluent (sub); 'Balanced' may be mobile/model-specific.

**Correction:** 'Balanced' (Standard) IS a distinct stream-quality option in the Reolink desktop Client, not just mobile. Official Reolink support docs explicitly instruct desktop Client users to right-click the live view and select "Clear / Balanced / Fluent," and to use the toolbar stream icon to switch among all three. Balanced/Standard is the mid-quality stream between Clear (main/high) and Fluent (sub/low). However, its availability is model-dependent: cameras that expose only two substreams will show just Clear and Fluent, so on some devices Balanced is absent — but this is a per-camera capability limitation, not because the desktop Client lacks the option.

Reolink's official support article "How to Change Stream Mode in Live Viewing" states for the desktop Client: right-click and select "Clear / Balanced / Fluent," and the article "Introduction to the Difference Between Clear, Fluent and Balanced/Standard Stream" defines Balanced/Standard as the quality between Clear and Fluent. Both explicitly cover the PC/desktop client, refuting the claim that docs confirm only Clear and Fluent for desktop and that Balanced is mobile-specific. The one true nuance is that Balanced is model/capability-specific (only cameras with a third stream expose it), so for a 1:1 Linux clone the option should be present but conditionally shown based on the camera's advertised stream count.

## ❌ REFUTED: md5_str_modern truncates the uppercase MD5 hex to 31 characters (util.py line ~116 uses hex[0:31])

**Correction:** Reolink's documented 31-character truncation applies to the plaintext PASSWORD, not to an MD5 hex digest. Reolink cameras/NVRs silently truncate any login password longer than 31 characters before it is sent, so clients slice the password with [:31] to match. An MD5 hex digest is always 32 characters, and there is no verifiable public Reolink code containing a function named md5_str_modern that truncates the uppercase hex to 31 chars via hex[0:31]. Note also that the modern Reolink JSON/CGI login API generally transmits the password (base64/plaintext over the Login command), not an MD5 hash, so the premise that the modern path even produces a truncated MD5 hex is unsupported.

No local util.py or md5_str_modern function exists in the working directory, and web searches for the exact identifier "md5_str_modern" returned nothing in any Reolink project. The only real, documented 31-character truncation in the Reolink ecosystem (fwestenberg/reolink_dev issue #104, corroborated by Home Assistant reolink-aio) is truncation of the plaintext password to 31 chars by the device itself, with clients applying password[:31] to match. That is a different object (the password) than what the claim describes (an MD5 hex digest). Truncating a hash to 31 of its 32 hex chars is also cryptographically nonsensical and is not something any documented Reolink auth scheme does. The specific file/line reference (util.py line ~116, hex[0:31]) cannot be confirmed in any public source and appears fabricated or conflated with the real password-truncation behavior. Because the described mechanism contradicts documented behavior and the cited artifact is unverifiable, the claim is refuted.

## ⚠️ PARTLY-TRUE: ONVIF default port is 8000 and Reolink does NOT support PTZ over ONVIF

**Correction:** Reolink's default ONVIF port is 8000, and Reolink PTZ cameras DO support PTZ (pan/tilt/zoom) over ONVIF.

The port half is correct: Reolink documents 8000 as the default ONVIF port (configurable in port settings). The PTZ half is false: Reolink PTZ-capable models (E1 Zoom, E1 Outdoor series, RLC-523WA, RLC-823 series, TrackMix, Argus Track, etc.) expose PTZ control through the ONVIF PTZ service, which is how ONVIF clients such as Blue Iris and iSpy move these cameras. Note ONVIF is a device-management/media web-services protocol layered over HTTP; port 8000 here is the Reolink-specific default for the ONVIF service endpoint rather than a universal ONVIF standard. For a native Linux client you would use the ONVIF PTZ service (or Reolink's own HTTP CGI API 'Ptz*' commands) to drive movement. Sources: Reolink support (Introduction to ONVIF Protocol; Ports Settings; Which Default Ports; PTZ articles) and Blue Iris/iSpy integration guides.

## ⚠️ PARTLY-TRUE: Reolink cameras output H.265 only at highest resolution and fall back to H.264 at lower resolution; audio is AAC with G.711 for two-way

**Correction:** The audio half is correct: Reolink cameras use AAC for the standard/recorded audio stream (not user-changeable) and G.711 for RTSP two-way audio. The video half is an oversimplification. It roughly holds only for high-resolution models: on 8MP (4K) cameras the main/"Clear" stream is H.265 and the sub/"Fluent" stream is H.264, and within the main stream the encoder switches to H.265 for resolutions >8MP and H.264 for lower. But 2MP/4MP/5MP cameras use H.264 for both streams and never output H.265 at all, and many newer PoE/WiFi models let you manually select H.264 or H.265 on the Clear stream. So codec is driven by model/stream type and user config, not purely by "highest vs lower resolution."

Reolink's official RTSP-format support article states: 8MP cameras use H.265 (main-stream) and H.264 (sub-stream); 2MP/4MP/5MP cameras use H.264 (some allow format changes). A separate Reolink article confirms that on 8MP cameras the main-stream format is H.265 when resolution is >8MP and H.264 when lower, and that select models expose an H.264/H.265 encoding-format toggle. Official docs also confirm audio is AAC (not changeable) and that two-way audio uses G.711. The claim's audio portion is fully confirmed; the video portion is directionally right for high-end cameras but wrongly generalized to all Reolink cameras and ignores manual codec selection.

## ⚠️ PARTLY-TRUE: Battery cameras (B800, Argus, E1) lack RTSP/ONVIF and require Baichuan; battery cams use UDP with a UID rather than IP

**Correction:** Reolink battery cameras (e.g. Argus series, Go, and the wire-free B-series like the Video Doorbell battery models) lack RTSP/ONVIF and instead use the proprietary Baichuan protocol (port 9000), reaching the camera via P2P over UDP using a UID with NAT hole-punching rather than a direct IP. However, the example list is miscategorized: the B800 is a WIRED 4K PoE camera (not battery) — it does correctly lack RTSP/ONVIF and use Baichuan, but it is NOT a battery camera. The E1/E1 Pro/E1 Zoom are WIRED indoor Wi-Fi/PT cameras that DO support RTSP and ONVIF, so they neither lack those protocols nor require Baichuan. Only the Argus family in the list is an actual battery camera lacking RTSP/ONVIF.

The underlying protocol facts are correct: Reolink confirms battery-powered cameras do not support RTSP/RTMP/ONVIF and rely on the proprietary "Baichuan" (port 9000) protocol; the reverse-engineered P2P remote protocol (Kaspars Dambis, neolink) uses UDP with a UID registered to p2p.reolink.com and NAT hole-punching to establish a direct connection rather than a plain IP. But the three named examples are wrong. B800 is a wired PoE camera, not battery (Reolink FAQ: "D800/B800 can not work with third-party software because they do not support RTSP/ONVIF... only work with our Reolink NVR"). E1/E1 Pro/E1 Zoom are wired indoor cameras that explicitly DO support RTSP and ONVIF per Reolink's own compatibility list and product pages. So the categorization is inaccurate even though the general claim about battery cams and the UDP/UID transport is accurate.

## ⚠️ PARTLY-TRUE: Login token leaseTime is 3600s and token is passed as a URL query param `token` on subsequent requests (confirmed in reolink_aio api.py lines ~1315-1346 and send() ~6019)

**Correction:** The token-as-query-param mechanism is confirmed by the code. In reolink_aio api.py, send() (lines ~6017-6021) sets param["token"] = self._token (or "null" for the Login command), and param is passed to aiohttp as params=param (lines 6067/6084, also GET), so `token` is sent as a URL query parameter on every non-login request. The leaseTime handling is at line 1345 — but it is NOT hardcoded to 3600 in api.py; the code reads leaseTime dynamically from the device's login response (json_data[0]["value"]["Token"]["leaseTime"]). 3600s (1 hour) is the typical default value returned by Reolink devices, not a constant asserted in api.py.

Verified against the reolink_aio main-branch api.py. Line 1345 sets _lease_time from the device-returned leaseTime; there is no literal 3600 in the token/login code (grep for 3600 returned nothing relevant). So the leaseTime value comes from the device (default 3600s on most Reolink firmware), and attributing '3600s' as 'confirmed in api.py' is inaccurate — the file reads it at runtime. The second half is fully confirmed: send() at lines 6019-6021 injects param['token']=self._token and aiohttp sends param as query-string params (params=param at 6067/6084), matching the cited ~6019. Cited line ranges are accurate (leaseTime at 1345, token in send at 6019).

## ⚠️ PARTLY-TRUE: Reolink HTTP API token expires after exactly 3600 seconds — commonly cited; confirm against current firmware behavior.

**Correction:** The Reolink HTTP API Login response returns a Token object with a `leaseTime` field, and that value is 3600 seconds (1 hour) on essentially all current firmware — so 3600s is the correct default/typical lifetime. However, 3600 is not a hard-coded protocol constant: it is a server-supplied value the device reports per login, and Reolink's own API guide describes it as the value the lease is "normally" set to. A correct client must READ `value.Token.leaseTime` from each Login response and re-login before it elapses (mature clients subtract a safety margin, e.g. ~60s), rather than assuming a fixed 3600.

Multiple independent sources — Reolink's official Camera HTTP API User Guide, the fwestenberg/reolink Python library used by Home Assistant, and community integrations (Domoticz, openHAB, iobroker) — consistently show the Login response as {"cmd":"Login","code":0,"value":{"Token":{"leaseTime":3600,"name":"..."}}}, with observed 3600 values across firmware from 2021 through 2025. So the "3600 seconds / 1 hour" figure is well-confirmed as the current default. What makes the claim only partly true is the word "exactly": the lifetime is not a fixed constant baked into the API — it is the device-reported leaseTime field, which Reolink documents as the "normal" lease (implying it can differ), and robust reference implementations parse it dynamically and apply a buffer rather than hardcoding 3600. There is also documented real-world nuance (e.g., Home Assistant issues about tokens being reused after expiry / invalidated early on some firmware), reinforcing that clients should not treat 3600 as an inviolable guarantee. For someone building a Linux NVR/client, the safe guidance is: default is 3600s, but read leaseTime from the response and refresh with margin.

## ⚠️ PARTLY-TRUE: P2P dispatcher hostname family is p2p.reolink.com and returns register/log/relay server addresses; reolink_aio uses UDP local port 2015

**Correction:** The P2P dispatcher hostname family (p2p.reolink.com, i.e. p2p0-p2p15.reolink.com, queried over UDP 9999) does act as register/dispatcher servers that return the addresses of register, logging, and relay servers — this part is correct. However, reolink_aio uses UDP port 2015 as the REMOTE connect port (UDP_CONNECT_PORT in reolink_aio/baichuan/udp_protocol.py, the device destination port), not a local port; its local UDP port defaults to 0 (an OS-assigned random port) unless explicitly overridden.

Part 1 is confirmed by reverse-engineering writeups (Kaspars Dambis) and Nozomi Networks: the p2p0-p2p15.reolink.com dispatcher/register servers reply with register, log, and relay server addresses. Part 2 is inaccurate in labeling: I cloned starkillerOG/reolink_aio and found UDP_CONNECT_PORT = 2015 in baichuan/udp_protocol.py, but it is passed as the remote/destination port (base connection port, stored as remote_port), while the local port is self._local_port which defaults to 0 (random). Port 2015 (with 2018) is Reolink's UDP broadcast/discovery/connect port on the device side, not a fixed local source port. So the claim is directionally right that reolink_aio uses UDP 2015, but 'local port' is wrong.

## ✅ CONFIRMED: HTTP API POST body must be a JSON array even for single commands and cmd is duplicated in the URL query string

Multiple independent Reolink API references confirm both halves of the claim. (1) POST requests to /cgi-bin/api.cgi carry a JSON array body even for a single command, e.g. [{"cmd":"GetAlarm","action":1,"param":{...}}], and the response is likewise always an array of objects. (2) The command name is also placed in the URL query string, e.g. ?cmd=GetAlarm&user=...&password=..., so cmd effectively appears both in the query string and inside the JSON body. This is documented in the Reolink Camera API User Guide (V8) and corroborated by community/GitHub examples such as: curl -s -k -X POST -H "Content-Type: application/json" -d '[{"cmd":"GetOnline","action":1}]' "https://IP/cgi-bin/api.cgi?cmd=GetOnline&user=USER&password=PASS". One nuance: for token/long-session auth the query string carries ?cmd=X&token=... ; for short-session it carries user/password. The cmd query parameter is commonly present, though some firmware tolerates its omission when cmd is in the body — but the standard/documented practice is to include it in both places, matching the claim.

## ✅ CONFIRMED: Baichuan/HTTP password limit is 31 characters — stated in Home Assistant docs; confirm it still holds on current firmware.

**Correction:** The 31-character maximum password length is real and still holds on current Reolink firmware. It stems from the Baichuan protocol's MD5 key derivation (31-char password + 32-char token + 1 null = 64-byte MD5 block); passwords over 31 chars are silently truncated at the camera login page and cause auth failures. Note: the number is documented in the reolink-aio library and GitHub issues/PRs (e.g. home-assistant/core PR #140789, reolink_dev issue #104), not literally in the current Home Assistant integration docs page — that page states the allowed character set (a-z, A-Z, 0-9, @$*~_-+=!?.,:;'()[]) rather than the 31-char length limit.

Multiple sources confirm a 31-character maximum. The limit is inherent to the Baichuan protocol's AES key derivation: the password is concatenated with a 32-character token and MD5-hashed, giving 31+32+1(terminator)=64 bytes matching the MD5 512-bit block; 32+ chars break authentication. Reolink cameras silently truncate at 31 chars during login, and current Reolink app/desktop clients plus reolink-aio (PR #140789) enforce this, so it holds on current firmware. The only imprecision in the claim is attribution: the current HA docs page describes allowed characters rather than explicitly stating the 31-char length limit, which is documented in the underlying library and GitHub discussions.
