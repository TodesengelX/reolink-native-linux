# Architecture Proposal: velocity-first

**Angle:** Fastest path to a working 1:1 replica and maximum developer velocity, while staying genuinely native (no Electron/WebView). The decisive lever is that the single largest chunk of work — the entire Reolink protocol surface (HTTP CGI JSON API + Baichuan events + discovery + PTZ + recording search/download) — already exists as reolink_aio under MIT, so the stack is chosen to REUSE that verbatim rather than reimplement it, and to spend engineering effort only on the UI and video panes where no permissive replica exists.

## Tech Stack

Python 3.12 + PySide6 (official Qt 6 for Python, LGPLv3): QML/Qt Quick for the video grid, live view, playback timeline and PTZ joystick; Qt Widgets for the dense Device/Client settings dialogs (hybrid via QQuickWidget). Device layer: reolink-aio (MIT) reused as-is, bridged into the Qt event loop with qasync over its native asyncio/aiohttp. Video engine: one embedded libmpv instance per pane (python-mpv) for reliable RTSP / HTTP-FLV H.264/H.265 hardware decode (VAAPI/NVDEC) rendered zero-copy into Qt; FFmpeg CLI (subprocess, stream-copy remux) for recording and JPEG snapshots; go2rtc (MIT) as an optional local restream sidecar for models with broken RTSP or H.265-over-WebRTC issues. Build/deps: uv (or PDM) for the Python environment; packaged as a Flatpak (primary, org.kde runtime for Qt + bundled libmpv/FFmpeg/VAAPI) and an AppImage.

## Rationale

The angle rewards reuse over rewriting. reolink_aio is MIT, Reolink-authorized, and already implements both the HTTP CGI API and the Baichuan push protocol that neolink (AGPL, cannot be copied) reverse-engineered — `pip install reolink-aio` collapses months of protocol work into a dependency and sidesteps every documented quirk (1h token leaseTime refresh, 31-char password limit, NVR channel indexing, cmd-in-URL-and-body). That single fact makes Python the highest-velocity language despite the video-heavy workload, because the performance-critical paths (decode, render, remux) all execute in native C (libmpv/FFmpeg/Qt), leaving Python only as orchestration where the GIL is irrelevant. PySide6 keeps the app genuinely native — the real Reolink desktop client is itself widely believed to be Qt, which de-risks pixel-level UI replication — and QML's scene graph is the natural fit for a custom dark skin, animated PTZ joystick, and a scrubbable color-coded timeline. Choosing libmpv over hand-rolled libav+DMA-BUF/EGL trades a little control for large velocity: mpv already solves Reolink's ugly-RTSP/H.265 edge cases, per-tile sub-stream playback, and hwdec fallback across Intel/AMD/NVIDIA, so a 16-pane grid becomes "16 configured players" rather than a from-scratch zero-copy render backend. LGPLv3 (PySide6, dynamically linked) plus MIT (reolink-aio, go2rtc) and LGPL-configured libmpv keep the whole stack redistributable, and Flatpak/AppImage ship the Qt/mpv .so files separately for compliance. If a specific pane ever needs tighter control than libmpv gives, the escape hatch is a small C++/FFmpeg QRhiWidget tile dropped in behind the same QML interface — without changing the rest of the app.

## Architecture Layers

| Layer | Responsibility | Key Libraries |
|---|---|---|
| UI / Presentation (native shell) | Reolink-faithful dark UI: left device list + add-device wizard (auto/LAN/IP/UID), Live View grid with 1/4/9/16 layouts, maximize/scrollview, floating per-pane toolbar (stream Clear/Balanced/Fluent, snapshot, record, talk, PTZ, digital/optical zoom), Playback page (calendar with recording dots, color-coded zoomable timeline, alarm-type filters, speed/frame-step, clip-cut download), and the five Device Settings groups plus Client Settings. QML for grid/live/playback/PTZ + overlays; Qt Widgets embedded for form-dense settings dialogs. | PySide6 (Qt 6 Quick + Widgets), QML/Qt Quick Controls, QQuickWidget for the widgets/QML bridge |
| Video panes (decode / render / capture) | Per-tile live playback pulling each camera's SUB-stream for the grid and switching to MAIN only on a maximized pane; hardware decode with software fallback; snapshot and manual-record; low-latency RTSP-over-TCP tuning. Recording is stream-copy remux (no re-encode) so all main streams can record while only sub-streams decode for display. | libmpv via python-mpv (embedded per pane, hwdec=auto VAAPI/NVDEC), FFmpeg CLI subprocess for remux-record + JPEG snapshot, go2rtc (MIT) optional restream sidecar for broken-RTSP / H.265 models |
| Device / Protocol API | Everything that talks to cameras/NVRs: discovery, login/token lifecycle, GetAbility-driven capability gating (PTZ vs fixed, AI vs motion, 2nd vs 3rd stream for Balanced), Get/Set of Enc/Isp/Osd/Mask/Rec/Alarm/AI/PTZ/network/storage/system, recording Search, Download/NvrDownload, and Baichuan real-time motion/AI/visitor event push. Reused wholesale, not reimplemented. | reolink-aio (MIT) — HTTP CGI + Baichuan; aiohttp (its transport); optional onvif-zeep for event fallback |
| App core: async bridge, state & config | Marry reolink_aio's asyncio to Qt's event loop; expose per-camera state, capabilities, event streams, PTZ presets, and layout as observable models bound into QML; persist device list, credentials (secret store), per-camera stream choices, and last-used grid layout/pane assignments across restarts; drive token-refresh and event subscription timers. | qasync (asyncio↔Qt loop), Python asyncio, QAbstractItemModel, Pydantic for config schemas, SQLite/JSON store, libsecret/keyring for credentials |
| Build / packaging / runtime | Reproducible dev env and native, driver-aware distribution bundling Qt, libmpv, FFmpeg and VAAPI so hardware decode works on end-user machines; two distribution channels. | uv or PDM (env/deps), Flatpak (primary, org.kde runtime), AppImage (secondary), optional PyInstaller for a .deb-style bundle |

## Risks

- Python at 16-pane scale: acceptable only because decode/render/remux run in native libmpv/FFmpeg/Qt; the GIL is fine for orchestration but per-tile UI updates and event fan-out must stay off the hot path. Mitigation: sub-stream-only grid, present-latest frame policy, and a C++/FFmpeg QRhiWidget tile escape hatch behind the same QML interface if a pane needs finer control.
- Video reliability on real Reolink models: several have 'awful' RTSP, and H.265 main streams break common fast paths. libmpv absorbs most of this, but plan the go2rtc HTTP-FLV restream fallback from day one and default the grid to the H.264 sub-stream.
- Battery/WiFi-only cameras (Argus/Go family) have NO RTSP/ONVIF and need Baichuan for VIDEO. reolink_aio's Baichuan covers events (and some control), not battery-cam video streaming; neolink does but is AGPLv3 (study-only, cannot be copied). Treat battery-cam live video as a Phase 2 item, likely via a neolink/go2rtc bridge process rather than in-app code, to avoid license contamination.
- 1:1 pixel-exact skin replication is a large, irreducible UI effort regardless of stack — QML lowers it but does not remove it; scope the custom timeline, PTZ joystick, and floating toolbar as real work, and confirm exact grid presets/persistence and whether Balanced is exposed per-camera.
- Dependence on upstream reolink_aio for per-model command routing (its runtime baichuan_cmds/broken_cmds lists) means new/odd firmware may need upstream fixes; pin versions and be ready to carry a fork patch.
- Two-way audio (talkback) is covered by neither libmpv nor reolink_aio's public video path — it needs an ONVIF RTSP G.711 backchannel or Baichuan talk implementation, a bespoke component to build and test with Wireshark.
- Packaging Python + Qt + libmpv + FFmpeg + VAAPI drivers into Flatpak/AppImage with working hardware decode across Intel/AMD/NVIDIA (and X11 vs Wayland) is fiddly and needs early validation on each target GPU; NVIDIA in particular diverges on zero-copy interop.
- Security/remote access: HTTP CGI sends credentials in cleartext and modern firmware ships RTSP/ONVIF/RTMP disabled by default — require HTTPS, and note that UID/P2P remote access depends on Reolink's relay infrastructure and reverse-engineered handshakes that can change.
